## 1. ★ 先に申し上げたい最大の論点：時間（AP）の設計

ここを決めないと、実装しても**ゲームのバランスが崩壊します。**

### いまの仕組み

```
1日 = 3AP ／ 卒業まで135日 ＝ 一生分でも 405AP
依頼1件 = 1AP = 戦闘1回
```

### 探索にすると何が起きるか

ご提示の流れ（村→草原→森→洞窟→ボス）を1回の依頼で行うと、
**道中の戦闘が4〜6回**発生します。

| | いま | 探索にすると |
|---|---|---|
| 1AP あたりの戦闘数 | 1回 | **5〜7回** |
| 1AP あたりの経験値（F級） | 92 | **約500**（5倍） |

**このままだと、学院の3年間という時間設計が成立しなくなります。**
（Phase 0 の STEP 15 で、難易度の崖を実測で見つけたのと同じ種類の問題です）

### 対処の案（ご判断をお願いします）

| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| **A** | 依頼のAPは今までどおり先払い。**道中の戦闘の報酬を下げる**（例 経験値×0.35） | 実装が簡単。AP設計を触らない | 雑魚を倒す旨みが薄い |
| **B** | **移動1区間ごとにAPを消費**（村→草原で1AP） | 「遠出は大仕事」という手応え | 1日3APでは1往復もできない。AP設計の作り直しが必要 |
| **C** | 探索専用の「スタミナ」を新設 | APを触らない | 数字が2つになり分かりにくい（STEP 9 で一度見送った案） |
| **D** | **依頼ごとに必要APを引き上げる**（例：森の依頼は3AP） | 距離感が出る | 1日1件しか受けられなくなる |

> **私の推奨は A です。**
> 理由：APの設計（1日3AP・135日）は**学院生活の根幹**で、ここを動かすと
> 試験・学費・進級のすべてを測り直すことになります。
> 一方、道中の報酬倍率は**1か所の定数**なので、既存の測定ツールで
> すぐ確かめながら調整できます。

## 2. マップ方式（ご質問1）

### 3つの選択肢を、既存コードとの相性で比べました

| 方式 | 既存コードの流用 | スマホ操作 | 実装量 | 「歩く感覚」 |
|---|---|---|---|---|
| **① 完全自由移動**（タイルマップを歩く） | **ほぼ無い**（描画・当たり判定を新規） | 方向キーが必要。画面が狭い | **大** | ◎ |
| **② ノード型**（地点をタップして移動） | 高い | タップのみ。**最も安定** | 小 | △ |
| **③ 中間：ノード＋区間の歩行** | **高い** | **タップのみ** | 中 | **○** |

### 推奨：**③ 中間方式**

```
地図（ノード）        村 ─── 草原 ─── 森 ─── 洞窟 ─── ボスの間
                      ↑ タップで隣の地点へ出発

移動中（横スクロール）  ▶ パーティが右へ歩く演出
                      ├─────●───────┤  進行度
                      1歩ごとに遭遇判定
                      ⚔ 敵出現 → 戦闘 → 戻って続きから
                      到達 → 地点の画面へ
```

**この方式を推す理由**

1. **既存の歩行演出がそのまま使えます。**
   `G.UI.walkTo()`（ui.js）が、すでにパーティを横に歩かせる演出を持っています。
   スプライトには `is-walk` のアニメーションも実装済みです。
   ここを「700ミリ秒で終わる演出」から「進行度つきの移動」に育てます。

2. **スマホで最も確実です。**
   STEP 13 の監査で、この画面サイズでは**方向キーを置く余白がない**ことが
   分かっています（戦闘コマンドですら画面外に出ていました）。
   タップだけで完結する方式が、いちばん失敗しません。

3. **「歩いている感覚」は出せます。**
   進行度バー・歩数・パーティの歩行アニメ・背景の流れで、
   「いま移動の途中だ」という手応えは作れます。

> ①の完全自由移動は、**ゲームとしては魅力的ですが**、
> 描画・当たり判定・方向キーをすべて新規に作ることになり、
> いまの戦闘・学院・ギルドと噛み合わせる作業が大きくなります。
> **まず③で通しで遊べる形を作り、物足りなければ①へ育てる**ことをおすすめします。

## 3. プレイヤーの移動方式（ご質問2）

### 採用：**タップのみ**

| 操作 | 動作 |
|---|---|
| 地図で**隣の地点をタップ** | そこへ向けて出発 |
| 移動中に**画面をタップ** | 演出を飛ばして即到着（せっかちな人向け） |
| 移動中に**「引き返す」** | 村方向へ戻る |

**方向キー・スワイプは採用しません。**理由：

- 方向キーは画面下部に120px前後を占有します。STEP 13 の実測では、
  iPhone SE でその余白がありません
- スワイプはブラウザの「戻る」ジェスチャと競合し、iPhoneで誤作動しやすい

**ボタンは44px以上**にします（STEP 13 の基準）。

## 4. 地点データ構造（ご質問3）

ご指定の項目をすべて持たせます。**新規ファイル `src/data/places.js`** に置きます。

```js
G.SPOTS = {
  village_01: {
    id: 'village_01',
    name: 'ラヴィンの村はずれ',
    x: 10, y: 50,                    // 地図上の位置（%）
    type: 'town',                    // town / field / dungeon / boss / event
    area: 'plains',                  // 既存の G.AREAS と結ぶ鍵
    description: '旅の始まる場所。ここから先は魔物が出る。',
    requiredLevel: 1,
    recommendLv: [1, 5],
    enemies: [],                     // 村なので戦闘なし
    boss: null,
    reward: null,
    unlock: { },                     // 解放条件（空 = 最初から）
    links: ['field_01'],             // 隣接する地点
    steps: 0,                        // ここまでの道のり（歩数）
    encounterRate: 0,
    events: [],                      // 将来の宝箱・NPC・回復点をここに
  },

  field_01: {
    id: 'field_01', name: '草原の道', x: 28, y: 44,
    type: 'field', area: 'plains',
    description: '見通しのよい草原。スライムがよく出る。',
    requiredLevel: 1, recommendLv: [3, 8],
    enemies: ['slime', 'rat', 'goblin', 'wild_wolf'],   // ← G.AREAS.plains.pool から
    boss: null, reward: null,
    unlock: { }, links: ['village_01', 'forest_01'],
    steps: 6, encounterRate: 0.22,
    events: [],
  },
  // forest_01 / cave_01 / boss_01 も同じ形
};
```

### 「進行状況」はデータに書かない

ご指定の `unlocked` / `cleared` は、**データ側ではなくセーブ側**に持ちます。

```
G.SPOTS        … 変わらない設計図（解放条件・敵・報酬）
d.explore      … その人の進み具合（到達済み・撃破済み・現在地）
```

理由：データに `unlocked:true` と書くと、**新しく始めても解放されたまま**になり、
2周目やセーブの引き継ぎで破綻します。
（Phase 0 STEP 10 の「解放済み一覧は保存せず、条件から毎回計算する」と同じ考え方です）

## 5. エンカウント方式（ご質問4）

```
移動開始 → 1歩進む → 乱数判定 → 出れば戦闘 → 勝てば同じ歩数から再開
                ↑                              ↓
                └──────────────────────────────┘
                        残り歩数が0になったら到達
```

### 調整できる値（すべてデータ側）

```js
encounterRate: 0.22,     // 1歩あたりの遭遇率
steps: 6,                // その区間の歩数
minSafeSteps: 1,         // 最初の1歩は必ず安全（出発直後の被弾を防ぐ）
maxRun: 3,               // 3歩続けて出たら、次は必ず出ない（連戦の防止）
```

**「毎回戦闘でストレス」を防ぐ仕掛けを2つ入れます。**

- **連続で出すぎない**：3連続で遭遇したら次は必ず安全
- **間が空きすぎない**：5歩出なかったら次は必ず遭遇（ダレ防止）

> **乱数は必ず `G.util.rand()` 系を通します。**
> `Math.random()` を直接呼ぶと、`npm test` の照合（乱数を固定して
> 結果を突き合わせる仕組み）が効かなくなります。

## 6. クエストとの連動（ご質問5）

### 既存の依頼は削除しません（ご指示どおり）

`G.QUESTS`（23件）は**そのまま残し**、**意味を変えます**。

| | いま | 変更後 |
|---|---|---|
| 受注すると | **即座に戦闘が始まる** | **目的地が設定される** |
| `enemies` | 戦う相手そのもの | **目的地のボス編成**として使う |
| `area` | **どこからも読まれていない**（STEP 8 の調査より） | **目的地の決定に使う** |
| 達成条件 | 戦闘に勝つ | **目的地に到達してボスに勝つ** |

**既存データに足すのは2項目だけ**です。

```js
{ id:'q_slime', ..., area:'plains',
  target: 'field_01',        // ← 追加：目的地
  flavor: '麦畑の奥でスライムが増えているらしい',  // ← 追加：道中の説明
}
```

`area` はすでに23件すべてに書かれているので、**目的地の割り当ては機械的にできます。**

### 進行状況の持ち方

```js
d.quest = {
  active: 'q_slime',      // 受注中の依頼（1件）
  target: 'field_01',     // 目的地
  reached: false,         // 到達したか
}
```

## 9. 戦闘システムとの接続（ご質問7）

### ★ `battle.js` には一切触れません

既存の呼び出し方をそのまま使います。**新しい戦闘システムは作りません。**

```js
// 探索側から呼ぶ。いまギルドがやっているのと同じ形。
G.BattleUI.start(enemyIds, {
  canFlee: true,           // ボス戦では false
  intro: '……',
  onEnd: out => {
    // out = { result, exp, gold, drops, levelReports }
    if (out.result === 'win') {
      // 探索を再開 or ボスなら依頼達成へ
    } else if (out.result === 'lose') {
      // 村へ戻される
    } else {
      // 逃走：その場に留まる
    }
  },
});
```

**HP・MP・経験値・ゴールド・アイテムは、`G.Battle.finish()` が
すでに確定させています**（`battle.js:583`）。探索側で計算し直す必要はありません。

### 戦闘への出入り

```
探索画面 →（暗転0.3秒）→ 戦闘画面 →（勝利）→ 暗転 → 探索画面（同じ歩数から）
```

`G.UI.current` を戦闘中は `'battle'` にするため、
**下部タブが隠れる・戻るボタンで抜けられない**という既存の仕組みが
そのまま働きます（STEP 13 の修正）。

## 14. 既存機能への影響（ご質問10）

| 機能 | 影響 |
|---|---|
| **戦闘** | **なし**（呼び出し方は今と同じ） |
| 学院（授業・試験・進級） | **なし** |
| 転職・成長 | **なし** |
| ショップ・装備 | **なし** |
| 魔王城 | **なし**（別の仕組みのまま） |
| 昇格試験 | **なし**（ギルドで戦う形を維持） |
| **ギルドの依頼** | **意味が変わる**（戦闘 → 目的地の指定）。データは残す |
| **セーブデータ** | **項目が2つ増える**（`d.explore` / `d.quest`） |
| ゲームバランス | **1章の判断次第**。私の推奨は「道中の報酬に倍率」 |

### ★ セーブデータについての注意

いまのセーブには**バージョン管理の仕組みがありません**（STEP 10 で設計済み・未実装）。
項目を足すこと自体は `G.State.migrate()` で対応できますが、
**この機会に STEP 10 のセーブ作り直しを先に済ませたほうが安全**です。

| 順序 | 利点 | 欠点 |
|---|---|---|
| **セーブ → 探索** | 以後の項目追加がすべて安全になる | 探索の着手が遅れる |
| **探索 → セーブ** | すぐ遊べる形になる | いま遊んでいる人のセーブを一度壊す可能性 |

> ご自身が唯一のプレイヤーであれば、**探索を先**でも問題ありません。
> 公開後であれば、**セーブを先**にすべきです。
