# キャラクター表示システム 改修設計案

作成日：2026-09-23 ／ この文書の時点でコードは1行も変更していません。

---

## 0. 先に結論

**いまのキャラクターが「仮素材に見える」のは、絵が下手だからではなく、
「コードで図形を組み立てる方式そのものの限界」に達しているからです。**

現在のキャラクターは `src/ui/sprites.js`（1,271行）が、
SVGのパス（`<path d="...">`）を文字列として組み立てて描いています。
この方式では、

- 髪の毛の流れ、布のしわ、金属の質感といった「情報量」が出せない
- 職業ごとの差は「色」と「持ち物の形」でしか付けられない
- 1体の見た目を直すのに、数値を手で調整して何度も描き直すことになる

ため、どれだけ手を入れても「図形の組み合わせ」の域を出ません。
ご要望の「正式リリースを目指しているスマホRPG」に届かせるには、
**描画方式を、絵（画像素材）を貼る方式へ切り替える**のが正しい判断です。

そのうえで、この設計案では
**「絵がまだ1枚も無い状態でも、いまと同じようにゲームが動く」**
ことを最優先にしています。画像は後から1枚ずつ足せます。

```
screen_status.js  G.Sprite.hero(c)
screen_travel.js  G.Sprite.hero(c)
screen_job.js     G.Sprite.hero(...) ×3
```

## 2. 画像・CSS・SVG を管理している場所

**現状、画像ファイルは1枚も存在しません。**

| 種類 | 置き場所 | 内容 |
|---|---|---|
| キャラの形 | `src/ui/sprites.js` のJS文字列 | SVGパスをコードで生成 |
| 配色 | `G.SPRITE_PAL`（5系統）、`G.SPRITE_JOB[].pal`、`G.SPRITE_TINT` | 16進の色コード |
| 動き | `assets/style.css` の `.chr` 以下 | CSSアニメーション |
| 唯一のPNG | `pwa/icon-*.png` | アプリのホーム画面アイコン。キャラではない |

### 「外部画像は読み込めない」という制約の再検証

`sprites.js` の冒頭に「外部画像は読み込めない（配信時にブロックされる）」と
書いてありますが、**これは配信形態ごとに事情が違います。実測し直しました。**

| 配信形態 | 外部画像ファイル | 判定 |
|---|---|---|
| PWA（`dist/pwa/`） | 置ける（現に `icon-512.png` を配信中） | **◎ 使える** |
| スマホアプリ（Capacitor） | 置ける | **◎ 使える** |
| 公開リンク（Artifact） | 付随ファイルとして配信可能 | **◯ 使える** |
| **1ファイル版（ダウンロード）** | **置けない** | **× 埋め込みが必要** |

つまり、**本当に制約があるのは「1ファイル版」だけ**です。
そしてこれは **data URI（画像をテキストに変換して埋め込む）** で解決できます。

実測した膨らみ率：**1.33倍**（`pwa/icon-512.png` 137,920B → 183,896B）

## 3. キャラクター情報を管理しているデータ構造

### 3-1. 味方キャラ（`src/core/character.js` → `G.Char.create`）

```js
{
  key, name, icon,        // icon は絵文字1文字（'👧' など）
  isPlayer,
  level, exp,
  jobId,                  // ← 見た目はここから決まる
  jobHistory, jobPath,
  growthBonus, stats, hp, mp,
```

## 5. 戦闘中のキャラクター表示

```
.scene（248px / ボス戦 298px）
 ├ .scene-foes    敵 1〜3体（右奥・0.92倍に縮小）
 │   └ .unit > .unit-sprite（72×88px）> svg.chr.foe
 └ .scene-heroes  味方 4人（左手前）
     └ .unit > .unit-sprite（72×88px）> svg.chr
```

- 敵は `.chr.foe` に `transform:scaleX(-1)` を掛けて左右反転
- 動きは `.chr` に付けたCSSクラスで制御（`is-walk` `is-attack` `is-cast`
  `is-hurt` `is-down` `is-enter`）。**SVGの内部パーツ（`.s-armF` `.s-legF` 等）を
  個別に回転させている**
- 立体感は、同じ形を3回重ねて上2枚をCSSマスクで影・光にしている

> **ここが移行最大の争点です。**
> いまの「腕だけ振る」「脚だけ交互に動かす」は、体がパーツに分かれているから
> できています。1枚絵にすると**この動きは失われます**。
> 代替案は §7-4 に書きました。

## 7. 画像素材へ移行する場合の最適な構造

### 7-1. 基本方針：「表示システム」と「素材」を完全に分ける

```
  ゲームのコード            画像の索引               画像ファイル
  ────────────            ──────────               ────────────
  G.Sprite.hero(c)   →    G.ART.resolve(...)   →   assets/characters/...
        ↑                       ↑
   9か所の呼び出しは        ここだけが
   一切変えない             差し替えの窓口
```

**差し替える人が触るのは `assets/characters/` の中だけ**にします。
ファイル名の規則さえ守れば、コードは1行も触らずキャラが変わります。

### 7-2. フォルダ構成

```
assets/characters/
  manifest.json              ← どの画像が存在するかの一覧（自動生成）
  player/
    male/    battle.webp  field.webp  portrait.webp  face.webp
    female/  battle.webp  field.webp  portrait.webp  face.webp
  jobs/
    swordsman/   male/battle.webp  female/battle.webp  …
    archmage/    …
  companions/
    riina/   battle.webp  field.webp  portrait.webp  face.webp
    velt/    …
    noa/     …
  npc/
    villager_m/  portrait.webp  face.webp
    shopkeeper/  …
  monsters/
    slime/   battle.webp  face.webp
    goblin/  …
  bosses/
    cave_guardian/  battle.webp  portrait.webp
    demon_lord/     …
```

### 7-3. 用途ごとの素材仕様（4種類）

| 用途 | 使う画面 | 推奨サイズ | 比率 | 備考 |
|---|---|---|---|---|
| **battle** 戦闘立ち | 戦闘 | **384×480** | 4:5 | 足元を画像の下端に揃える |
| **field** 小型 | 拠点・街・探索・移動演出 | **192×240** | 4:5 | battleの縮小ではなく**描き起こし推奨**。小さくても分かる輪郭に |
| **portrait** 立ち絵 | 状態・転職・会話 | **512×768** | 2:3 | 腰から上。会話で使うので表情が要 |
| **face** 顔 | 仲間一覧・行動選択・道具の対象選び | **128×128** | 1:1 | いまの絵文字の置き換え |

**共通仕様**

| 項目 | 指定 |
|---|---|
| 形式 | **WebP**（第一候補）／PNG（代替）。どちらも透過必須 |
| 背景 | **完全透過**。影は描かない（CSS側で足す） |
| 向き | **すべて右向き**。敵は表示時にCSSで左右反転する |
| 余白 | 上下左右に3%。反転や揺れで切れないように |
| 画素密度 | 表示サイズの2倍（スマホの高精細画面向け） |
| 1枚の上限 | **40KB**（WebP品質80前後が目安） |
| 色 | 背景が暗い紫（`#120d1c`）なので、**輪郭に明るい縁取り**を入れると沈まない |

### 7-4. 「動き」をどうするか（最大の論点）

1枚絵にすると、いまの「腕を振る・脚を動かす」は失われます。3案あります。

| 案 | 内容 | 見え方 | 手間 |
|---|---|---|---|
| **A. 1枚絵＋体ごと動かす** | 画像1枚を、拡大縮小・傾き・揺れで動かす | スマホRPGとして十分。多くの市販ゲームがこの方式 | **小**（画像1枚/用途） |
| **B. 2〜3枚の差分** | 待機/攻撃/被弾の3枚を切り替える | かなり良い | 中（画像3倍） |
| **C. パーツ分割を維持** | 画像を頭・胴・腕・脚に分けて貼る | いまと同じ動き | 大（画像4倍＋位置合わせ） |

**おすすめは A です。**
理由：画像の枚数が最小で、AIで生成した絵をそのまま使えます。
Bは「気に入った絵ができてから」追加投資として後乗せできます。

### 7-5. 絵が無いときの動き（ここが設計の肝）

```
  battle.webp を要求
        ↓
  manifest に有る？ ── 有る → その画像を表示
        ↓ 無い
  同じ職の別の性別は？ ── 有る → それを表示
        ↓ 無い
  同じ系統の代表画像は？ ── 有る → それを表示
        ↓ 無い
  いまのSVG描画に戻る  ← ★ ここが最後の受け皿
```

**いまの `sprites.js` は消しません。**
「まだ絵が用意できていないキャラ」を埋める土台として残します。
これにより、**画像を1枚も用意しない状態でもゲームは今日と同じに動き、
1枚入れるごとにそのキャラだけが新しい絵になります。**

## 8. 既存機能への影響

| 項目 | 影響 | 対応 |
|---|---|---|
| **戦闘エンジン** `src/core/battle.js` | **影響なし**（画面を一切知らない設計） | 触らない |
| **層の規則** data→core→ui | 画像索引は ui 層に置けば違反なし | `src/ui/art.js` |
| **セーブデータ** | `look`（性別など）追加 → 旧セーブに無い | `migrate()` で既定値を補う（前例あり） |
| **スプライト照合** `tools/sprite-check.js` | **185通りの基準が全部変わる** | 「SVG版」と「画像版」を別々に照合する形へ |
| **1ファイル版** | 外部画像が使えない | data URI で埋め込む（§9） |
| **PWAのオフライン** `pwa/sw.js` | 画像を保存対象に入れないとオフラインで消える | 生成時に一覧へ自動追加 |
| **表示の速さ** | 画像が増えると初回が重くなる | 画面ごとに必要な分だけ読む |
| **アプリの容量** | 1ファイル版が膨らむ | §9で試算 |

### 容量の試算（実測の 1.33 倍で計算）

| 素材の範囲 | 枚数 | 生データ | 1ファイル版の増分 | 合計 |
|---|---|---|---|---|
| 最小（主人公2＋仲間3＋敵8の battle のみ） | 13 | 約 0.4MB | 約 0.5MB | **約 0.9MB** |
| 標準（主人公・仲間・25職・32敵の battle＋face） | 約 130 | 約 3.4MB | 約 4.5MB | **約 4.9MB** |
| 全部（4用途 × 全キャラ＋NPC） | 約 400 | 約 10MB | 約 13MB | **約 13.4MB** |

現在の1ファイル版は **423KB**。公開リンクの上限は **16MB** です。

> **「全部」は上限ぎりぎりで危険です。**
> 1ファイル版には **battle と face だけ** を埋め込み、
> portrait（大きい立ち絵）は PWA版・アプリ版だけで読む、という
> **配信形態ごとの出し分け**をおすすめします。

## 10. おすすめのキャラクター素材仕様（ID体系）

### 10-1. キャラクターID

| 区分 | ID規則 | 例 |
|---|---|---|
| 主人公 | `player` ＋ `look.sex` | `player` / male, female |
| 仲間 | `G.COMPANIONS` の鍵をそのまま | `riina` `velt` `noa` |
| 職業 | `G.JOBS` の鍵をそのまま | `swordsman` `archmage` `saint` |
| NPC | `npc_` ＋ 種別 | `npc_villager_m` `npc_guild_staff` |
| 敵 | `G.ENEMIES` の鍵をそのまま | `slime` `orc` `harpy` |
| ボス | `G.ENEMIES` の鍵をそのまま | `boss_cave_guardian` `demon_lord_2` |

**既存のIDをそのまま使います。** 新しい対応表を作らないことで、
「IDの二重管理でズレる」という事故を最初から避けます。

### 10-2. ファイル名の規則

```
<用途>.webp                      性別の区別が要らないもの
<用途>_<性別>.webp               主人公・職業

  用途   battle / field / portrait / face
  性別   m / f
```

例：

```
assets/characters/player/battle_m.webp
assets/characters/player/portrait_f.webp
assets/characters/jobs/swordsman/battle_m.webp
assets/characters/jobs/swordsman/battle_f.webp
assets/characters/companions/riina/face.webp
assets/characters/monsters/orc/battle.webp
assets/characters/bosses/cave_guardian/battle.webp
```

## 11. 移行方法

### いまのキャラクター → 新しいキャラクターシステム

```
【現在】
  screen_battle.js → G.Sprite.hero(c) → SVG文字列 → 画面

【移行後】
  screen_battle.js → G.Sprite.hero(c) ─┬→ 画像あり → <img src="...">
       ↑ ここは変えない                └→ 画像なし → 今までのSVG
```

`G.Sprite.hero()` の中身だけが変わります。呼び出し側9か所は無変更です。

新しく作る `src/ui/art.js` の骨子：

```js
G.Art = {
  manifest: {},                       // build-art.js が埋める

  /* kind: 'player'|'companion'|'job'|'npc'|'monster'|'boss'
   * use : 'battle'|'field'|'portrait'|'face'
   * look: { sex:'m'|'f' }
   * 戻り値：画像のURL（data URI のこともある）。無ければ null */
  of(kind, id, use, look) { ... },

  /* 画像が無いときに代わりに使えるIDを順に返す */
  fallbacks(kind, id) { ... },
};
```

`G.Sprite.hero()` への追加は、実質これだけです：

```js
hero(c, use) {
  const url = G.Art && G.Art.of(c.isPlayer ? 'player' : 'companion',
                                c.key, use || 'battle', c.look);
  if (url) return `<img class="chr art" src="${url}" alt="${G.util.esc(c.name)}">`;
  /* ↓ 以下、いまのSVG生成コードがそのまま残る */
  ...
}
```

### セーブデータの移行

`look` が無い古いセーブは、`migrate()` で `{ sex:'m' }` を補います。
探索システムを足したときと同じやり方で、前例があります。

## 12. 実装ロードマップ

### STEP 1：キャラクターシステム改修（画像は0枚のまま）

**目標：絵が1枚も無い状態で、いまと完全に同じ画面になること。**

1. `src/ui/art.js` を作る（`G.Art.of()` は常に null を返す状態から）
2. `G.Sprite.hero()` / `enemy()` に4行の分岐を足す
3. `character.js` に `look` を追加、`state.js` の `migrate()` で補完
4. `tools/build-art.js` を作る（画像0枚でも動く）
5. `tools/art-test.js` を作る

**確認：`npm test` 20項目が全部通り、`sprite-check` 185通りが全一致すること。**
つまり **見た目が1ピクセルも変わらない** のが合格条件です。

### STEP 2：キャラクター素材差し替え

1. `assets/characters/` のフォルダを作る
2. **まず1枚だけ**入れる（例：`monsters/slime/battle.webp`）
3. スライムだけが新しい絵になり、他が変わらないことを確認
4. 問題なければ、優先順に追加
   1. 主人公 男女（battle・face）
   2. 仲間3人（battle・face）
   3. 敵のうち序盤の8体
   4. Tier1・Tier2 の12職 × 男女
   5. ボス6体
   6. NPC・portrait

**各段階で `npm test` を通します。** 途中で止めても壊れません。

### STEP 3：各画面への反映

1. 用途ごとに正しい素材を使うようにする（`face` を仲間一覧へ、など）
2. **会話に立ち絵を出す**（`playStory` に `portrait`）
3. NPCを街・ギルド・学院に出す
4. 主人公の性別選択をタイトルに追加
5. 敵の `face` を図鑑・戦闘の対象選択に

### STEP 4：スマホ表示確認

1. `tools/mobile-audit.js` で押せる領域と見切れを実測
2. 393×852（iPhone）と 360×800（Android）で全画面を撮影して確認
3. 通信を切った状態でPWAが画像込みで動くか
4. 1ファイル版の容量を測り、16MBに収まるか
5. 読み込みにかかる時間の測定
