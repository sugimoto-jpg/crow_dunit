## 1. なぜ今やるのか

STEP 9（自由探索）でセーブデータに項目を足す予定です。
**構造を変える前に、変えても壊れない仕組みを作っておく必要があります。**

順番を逆にすると、STEP 9 を遊んだ人のセーブが、
その次の変更で読めなくなります。公開後にこれが起きると取り返しがつきません。

## 2. 現状（実測）

### 2-1. いまの仕組み

```
localStorage['tensei_arcana_save_v1'] = JSON.stringify(ゲーム状態)
```

**1つのキーに、1つのセーブ。それだけです。**

### 2-2. セーブデータの大きさ

実際にゲームを進めて測りました。

| 状態 | 大きさ |
|---|---|
| 開始直後 | 1.3 KB |
| 仲間4人 | 3.7 KB |
| Lv30×4人 | 5.4 KB |
| 全アイテム所持 | 6.2 KB |
| 図鑑全埋め | 6.7 KB |
| 冒険ログ60行 | 10.3 KB |
| **終盤（Lv65×4人）** | **10.9 KB** |

内訳（終盤）：

| 項目 | 大きさ | 備考 |
|---|---|---|
| `log`（冒険の記録） | 3.6 KB | **全体の1/3。最大60行** |
| `party` | 2.6 KB | |
| `roster`（仲間名簿） | 2.2 KB | **party と中身が重複している** |
| `inventory` | 0.9 KB | |
| その他22項目 | 1.6 KB | |

**ブラウザの保存領域は通常5MBです。**
つまり11KBのセーブなら、**スロットを10個作っても全体の0.2%**しか使いません。
容量は心配する必要がありません。

### 2-3. 壊れたデータを読ませたらどうなるか

10パターンを実際に食わせました。

|---|---|---|---|

| `player` が無い | **あり** | 失敗 | タイトルに留まる |

| 全く別の文字列 | **あり** | 失敗 | タイトルに留まる |

## 3. 見つかった問題（5件）

### ★ 問題1：「つづきから」が押しても何も起きない

壊れたセーブがあると、**ボタンは表示されるのに押しても進めません。**
「セーブデータを読み込めませんでした」と一瞬出て、それで終わりです。

原因は `hasSave()` が**キーの存在しか見ていない**ことです（`state.js:65`）。

```
hasSave() { return !!localStorage.getItem(G.SAVE_KEY); }
```

中身が壊れていても「セーブはある」と答えます。

**遊ぶ人にとっては、ゲームが完全に詰まった状態です。**
「はじめから」を押せば進めますが、それは**壊れたデータを上書きする**ことを意味し、
もし復旧できたかもしれないデータだったとしても永久に失われます。

### ★ 問題2：バックアップが1つも無い

セーブは1か所だけです。書き込みの途中で電池が切れたり、
ブラウザが強制終了したりすると、**そこで冒険の記録が消えます。**
戻す手段はありません。

### ★ 問題3：保存の失敗が誰にも伝わらない

`G.State.save()` は**32か所**から呼ばれますが、
**戻り値を見ているのは1か所だけ**です（`screen_home.js:102`）。

保存領域がいっぱいのときや、ブラウザのプライベートモードで
保存が禁止されているとき、`save()` は `false` を返して静かに終わります。
**遊ぶ人は保存されていると思ったまま遊び続け、閉じた瞬間に全部消えます。**

### ★ 問題4：値の中身が検査されていない

`migrate()`（`state.js:83`）は、難易度・戦闘速度・科目などを丁寧に直しています。
しかし**数値の検査がありません**。

所持金が文字列でも、日付がマイナスでも、そのまま読み込まれます。
そのあと計算に使われると、画面に `NaN` が出たり、
買い物ができなくなったりします。

### ★ 問題5：未来のセーブを黙って読む

`version: 99`（今より新しい形式）のセーブを、古いゲームが読んでしまいます。
読めた気になって、**古い形式で保存し直すと、新しい項目が消えます。**

これは、ストア公開後にアップデートを配信したとき、
「新しい端末で遊んだ続きを、更新していない端末で開く」場面で起きます。

## 4. 設計

### 4-1. 保存する場所の名前

```
ta.save.v2.slot1        スロット1の本体
ta.save.v2.slot1.bak    スロット1の直前の内容（自動バックアップ）
ta.save.v2.slot2        …
ta.save.v2.auto         オートセーブ枠
ta.save.v2.index        スロット一覧（一覧表示を速くするための索引）
tensei_arcana_save_v1   旧キー（読むだけ。消さない）
```

**旧キーを消さない理由**：いま遊んでいる人のデータです。
新形式に写したあとも残しておけば、万一の取り違えでも戻せます。
11KBなので残しても負担になりません。

### 4-2. スロット構成

| 枠 | 用途 | 保存のタイミング |
|---|---|---|
| オートセーブ | 自動 | 今までどおり（戦闘後・日付変更時など32か所） |
| スロット1〜3 | 手動 | プレイヤーが「保存する」を選んだとき |

**合計4枠 × 各2つ（本体＋バックアップ）＝ 最大約88KB**。
保存領域5MBの2%未満です。

### 4-3. 保存する形（封筒に入れる）

いまは「ゲーム状態をそのまま」保存しています。
これを**封筒に入れて**保存します。

```
{
  fmt:      2,              セーブ形式の番号（構造を変えたら上げる）
  game:     '1.0.0',        ゲーム本体のバージョン（表示用）
  savedAt:  1700000000000,  保存した時刻
  sum:      'a3f91c04',     中身の指紋（壊れていないかの確認用）
  meta: {                   一覧に出す情報だけを取り出したもの
    name:'アルト', level:32, day:78, term:5,
    gold:24500, job:'賢者', icon:'🧙',
  },
  data: { …ゲーム状態… }
}
```

**`meta` を別に持つ理由**：セーブ一覧を出すたびに11KBを全部読んで
解釈するのは無駄です。一覧には名前とレベルと日付しか要りません。
`meta` だけ読めば済むようにします。

**`sum`（指紋）**：`data` の中身から計算する短い値です。
読み込むときに計算し直して一致しなければ「壊れている」と分かります。
暗号ではありません。**改ざん防止ではなく、破損の検出**が目的です。

> 補足：ブラウザのセーブは、その気になれば誰でも書き換えられます。
> これは技術的に防げません（1人用ゲームなので実害もありません）。
> `sum` は「書き換え」ではなく「壊れ」を見つけるためのものです。

### 4-4. バージョン管理と移行

```
fmt = 1   いまの形（旧キー）
fmt = 2   封筒に入れた形（今回）
fmt = 3   STEP 9 で explore を足したとき
```

読み込みの判断：

| 状況 | 動作 |
|---|---|
| `fmt` が今と同じ | そのまま読む |
| `fmt` が**古い** | 1段ずつ変換して読む（2→3→4…） |
| `fmt` が**新しい** | **読まない。** 「このデータは新しいバージョンで作られています。アプリを更新してください」と表示 |

**1段ずつ変換する理由**：`1→5` の変換を直接書くと、
組み合わせが増えるほど関数が増え、必ずどこかが抜けます。
`1→2` `2→3` `3→4` `4→5` と並べて順に通せば、追加は常に1本で済みます。

いまの `migrate()` は**そのまま `1→2` の中身として使えます。**
よくできているので、作り直しません。

### 4-5. 値の検査を足す

`migrate()` に、数値の範囲検査を追加します。

| 項目 | 範囲 | 外れていたら |
|---|---|---|
| `gold` | 0 〜 9,999,999 | 0 |
| `day` | 1 〜 9999 | 1 |
| `ap` | 0 〜 `apMax` | `apMax` |
| `term` | 0 〜 8 | 0 |
| `termDay` | 1 〜 15 | 1 |
| `tuitionDue` | 0 以上 | 学年に応じた既定値 |
| レベル・HP など | 既存の `clampVitals` が担当 | — |

**数値でないもの（文字列・null・NaN）は、すべて既定値に戻します。**

### 4-6. 壊れていたときの復旧の流れ

```
スロットを読む
  ↓ JSONとして読めない／指紋が合わない／fmt が未来
バックアップ（.bak）を読む
  ↓ 読めた
「直前の記録から復元しました（3分前の状態です）」と伝えて続行
  ↓ バックアップも読めない
スロットを「⚠ 壊れています」と表示したまま残す
  ↓
「このスロットを削除する」を選んだときだけ消す
```

**大事な原則：壊れたデータを勝手に消さない。**

「はじめから」で上書きされて消える、という現在の動きをやめます。
壊れて見えても、あとから手で救える可能性があります。

### 4-7. 書き込む順番

保存領域には「まとめて書く」機能がありません。
そこで**順番で安全を作ります**。

```
1. いまの本体を .bak に写す
2. 新しい内容を本体に書く
```

1と2の間で中断しても、`.bak` には**1つ前の正常な内容**が残ります。
逆順にすると、書き込み失敗時に両方壊れます。

### 4-8. 保存に失敗したときの扱い

`save()` の戻り値を、成功/失敗だけでなく**理由**まで返す形にします。

| 失敗の理由 | 対処 |
|---|---|
| 容量がいっぱい | `log`（冒険の記録）を20行に減らして**1回だけ再挑戦**。それでも駄目なら下へ |
| 保存が禁止されている（プライベートモード等） | 下へ |

**失敗したら、その場でプレイヤーに伝えます。**

> 「保存できませんでした。ブラウザの設定で保存が制限されているか、
> 空き容量が足りない可能性があります。このまま遊べますが、
> 閉じると記録が残りません。」

ただし**同じ警告を何度も出しません**（STEP 6 のエラー表示と同じ考え方）。
1回のプレイで1度だけ出します。

`log` を最初に削る理由は、**セーブの1/3を占めていて、
削っても遊びに影響しないから**です（2-2 の実測より）。

### 4-9. `hasSave()` を直す

```
いま : キーが存在するか
これから : 読めて、指紋が合い、fmt が扱える範囲か
```

これで**「押せるのに進めない『つづきから』」が無くなります。**

## 5. スマートフォンアプリにしたときの保存先

### 5-1. 事実

Capacitor（STEP 14 で検討予定）でアプリにした場合、
**アプリの中身はブラウザとして動くので、`localStorage` はそのまま使えます。**

**ただし、これはストア公開には向きません。**

- iOS：アプリのWebView領域は、端末の空き容量が逼迫すると
  **OSによって削除されることがあります**
- Android：アプリのデータ削除やストレージ掃除の対象になり得ます

**「アプリを開いたらセーブが消えていた」は、実際に起きます。**

### 5-2. 対策：保存の出入口を1か所にまとめる

**今回の設計で一番大事な部分です。**

```
ゲーム本体
    ↓ 読む/書く（ここだけを使う）
G.Storage   ← 薄い1枚の層
    ↓
実際の保存先（差し替え可能）
  ・ブラウザ  … localStorage
  ・アプリ   … Capacitor Preferences（iOS/Android の正式な保存領域）
```

`G.Storage` が用意するのは4つだけです。

```
G.Storage.get(key)          読む
G.Storage.set(key, value)   書く
G.Storage.remove(key)       消す
G.Storage.keys()            一覧
```

**こうしておけば、アプリ化するとき `G.Storage` の中だけを差し替えれば済みます。**
ゲーム側のコードは1行も変わりません。

逆に、いまのまま `localStorage` を直接呼び続けると、
**32か所すべてを書き換える**ことになり、その過程で必ず漏れが出ます。

### 5-3. 非同期への備え

`localStorage` は即座に読み書きできますが、
**Capacitor Preferences は「待つ」必要があります**（非同期）。

そのため `G.Storage` は最初から**待てる形**（Promise）で設計します。
ブラウザでは即座に返るので、体感は変わりません。

**これを後から変えるのは大変です。**
最初から待てる形にしておくのが、唯一の現実的な選択です。

## 7. 実装の順序

**一度に作りません。**各段階でゲームが動く状態を保ちます（ルール5・7）。

| 段階 | 内容 | 確認方法 |
|---|---|---|
| 10-1 | `G.Storage`（薄い層）を追加。中身は `localStorage` のまま | 既存のセーブがそのまま読める |
| 10-2 | 封筒の形・指紋・`fmt` を導入。旧キーからの移行 | **旧形式のセーブを読み込むテスト** |
| 10-3 | `.bak` と復旧の流れ | **わざと壊して復旧を確認** |
| 10-4 | `migrate()` に数値検査を追加 | 10パターンの壊れデータで確認 |
| 10-5 | `save()` の失敗をプレイヤーに伝える | 保存を禁止した状態で確認 |
| 10-6 | スロットを3つに増やす／画面を作る | 通しテストに手順追加 |
| 10-7 | `hasSave()` を厳密にする | 「つづきから」の挙動を確認 |

**10-2 の前に、いまのセーブデータをファイルに書き出して保管します。**
移行の検証には「本物の旧データ」が要るためです。

### テストで必ず確かめること

STEP 6・7 と同じく、**わざと壊して落ちることを確認**します。

- 旧形式（`fmt` なし）のセーブが読めるか
- 途中で切れたデータから `.bak` で復旧できるか
- 未来の `fmt` を**読まずに**断るか
- 保存を禁止した状態で警告が出るか
- 10パターンの壊れデータで、**1つもゲームが壊れた状態にならないか**

## 9. この設計で守られること

- 戦闘エンジン（`battle.js`）には**一切手を入れません**

## 10. 付録：今回は直さないが、記録しておくこと

**`party` と `roster` が同じ仲間のデータを二重に保存しています**（2-2 の内訳）。
終盤で約2.2KB、セーブ全体の20%です。

`migrate()` が読み込み時に同じオブジェクトへ繋ぎ直しているので、
**遊ぶ上での不具合はありません。** 容量にも余裕があります。

直すなら「`roster` は仲間のキーだけを持つ」形にできますが、
セーブの構造を変える話なので、**今回の範囲には入れません。**
将来セーブが重くなったときの、最初の削りどころとして記録しておきます。
